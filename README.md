# Student Database Application System – Backend

A modular backend application built with **FastAPI** for managing student records through RESTful APIs, using **SQLite + SQLAlchemy ORM** for database operations and an integrated **Google Gemini AI assistant powered through LangChain** for answering natural-language questions about student statistics.

> **Project Note:** The frontend included in this repository is a lightweight demo client created primarily to visually test and interact with the backend APIs. The core deliverable of this project is the backend service.

---

## 🚀 Features

* RESTful APIs using FastAPI
* Student CRUD operations
* SQLite database
* SQLAlchemy ORM
* Pydantic request/response validation
* Duplicate email protection
* Proper HTTP status codes and error handling
* Swagger/OpenAPI documentation
* CORS configuration for frontend integration
* Google Gemini AI integration
* LangChain-based chatbot service
* Natural-language student statistics queries
* Controlled AI access to database statistics
* Automated API tests with Pytest
* Modular project architecture
* Simple frontend demo client
* Publicly deployed backend service

### AI Chat Flow

The chatbot does not directly execute arbitrary SQL queries generated by the AI.

Instead, the backend retrieves controlled student statistics from the database and provides that information to the Gemini-powered assistant.

```text
User Question
      ↓
FastAPI /chat Endpoint
      ↓
Chat Service
      ↓
Student Statistics from SQLite
      ↓
LangChain
      ↓
Google Gemini
      ↓
Natural-language Answer
```

This approach keeps database access controlled by the backend application and avoids unrestricted database operations by the AI model.

## 🤖 AI Assistant

The `/chat` endpoint allows users to ask natural-language questions about the available student statistics.

### Example Questions

```text
How many total students are there?

How many are male and female?
```

The backend calculates the available statistics from the SQLite database and provides the relevant information to the Gemini-powered assistant.

The AI assistant is instructed not to invent student information or answer questions beyond the statistics currently made available to it.

### Currently Available Statistics

The chatbot currently works with:

* Total number of students
* Number of male students
* Number of female students

This controlled approach keeps the chatbot focused on the supported student-statistics use case.

## 🧠 Vector Database Decision

A vector database was considered during the project research.

For the current Student Database Application System, a vector database was not integrated because the chatbot primarily works with **structured student records and statistical queries**. These queries can be efficiently retrieved directly from the SQLite database using SQLAlchemy.

Adding a vector database for these structured queries would introduce additional infrastructure and development complexity without providing a significant benefit to the current use case.

### Research Considerations

The vector database decision was considered using factors such as:

* Ease of integration
* Semantic and similarity search capabilities
* Scalability
* Development complexity
* Cost and free-tier availability
* Compatibility with the application architecture

### Future Extension

A vector database such as **Chroma** could be considered in a future version if the chatbot is extended to perform semantic search over unstructured content such as:

* Student documents
* Course descriptions
* Academic policies
* Training materials
* Other text-based knowledge sources

For the current structured student-statistics scope, SQLite with SQLAlchemy is sufficient.

## 🗄️ Database Design

The application uses SQLite as its relational database and SQLAlchemy as the ORM layer.

Student records contain fields such as:

| Field    | Description               |
| -------- | ------------------------- |
| `id`     | Unique student identifier |
| `name`   | Student name              |
| `age`    | Student age               |
| `gender` | Student gender            |
| `course` | Student course            |
| `email`  | Student email address     |

The database connection and session management are handled through `database.py`.

ORM models are defined in `models.py`, while database CRUD operations are separated into `crud.py`.

---

## 🔄 CRUD Operations

The backend provides the four fundamental database operations.

### Create

Adds a new student record.

```text
POST /students
```

### Read

Retrieves all students or a specific student.

```text
GET /students
GET /students/{student_id}
```

### Update

Modifies an existing student record.

```text
PUT /students/{student_id}
```

### Delete

Removes an existing student record.

```text
DELETE /students/{student_id}
```

All operations are exposed through FastAPI REST endpoints and can be tested using Swagger UI.

---

## ❗ Error Handling

The API returns appropriate HTTP responses for common error conditions.

Examples include:

* `404 Not Found` when a student does not exist.
* `409 Conflict` when a duplicate email is submitted.
* `422 Unprocessable Entity` when request validation fails.

Clear error messages are returned to help API consumers understand the problem.

## 🧩 Modular Architecture

The project separates different responsibilities into dedicated modules.

### `main.py`

FastAPI application entry point and API route definitions.

### `database.py`

Database engine, session configuration, settings, and database dependency.

### `models.py`

SQLAlchemy ORM database models.

### `schemas.py`

Pydantic request and response schemas.

### `crud.py`

Database CRUD operations.

### `services/chat_service.py`

AI chatbot logic, student-statistics retrieval, LangChain integration, and Gemini interaction.

This separation improves:

* Maintainability
* Readability
* Reusability
* Testing
* Scalability
* Separation of concerns
